technique/01 - first-principles.rs

#01 第一性原理 First Principles

// 把问题拆到不可再拆的公理，再从公理往上重建
拆到底之后剩下的东西出奇地少：一种请求方法、一个 token、一份 spec。下面 12 条公理就是整栋楼的地基。
Outline API 是纯 RPC 风格（全部 POST /api/resource.method），CLI 映射天然简单：documents.search → outline documents search，无需猜 REST 语义
spec 即契约：二进制不硬编码端点，CLI 本质是一个"专用于 Outline 的 OpenAPI 解释器"
每个操作真正需要的只有 (path, 参数 schema, auth)——内部用精简 IR（中间表示），不必保留完整 OpenAPI 模型
用 build.rs 在编译期把 spec 编译成 IR：保留动态架构的灵活性 + 零运行时解析成本
缓存 = 解析后的 IR 用 bincode 序列化到 ~/.cache/outline-cli，key 为 spec hash + CLI 版本
认证只是 Bearer token：keyring crate 进系统钥匙串，OUTLINE_API_KEY 环境变量兜底
全部请求都是 POST JSON，一个通用 request builder 覆盖 100% API——"客户端"核心约 100 行
CLI flag → JSON body 由 schema 驱动类型转换（"5" → int 按 schema 判断）
spec 漂移是核心风险——需要 outline spec sync 命令重新拉取上游 spec
响应美化才是真正的产品：JSON 输出是平凡的，人类可读的表格/markdown 渲染才是价值所在
架构本质两层：通用 OpenAPI 引擎 + Outline 风味的 UX 糖，拆成两个 crate
发送前本地 schema 校验：fail fast，错误信息比服务端 400 友好
基岩层小结：RPC 单形态 + spec 契约 + 两层架构 - 剩下的一切想法都建在这三块石头上。

technique/03 - scamper --ops SCAMPER

#03 SCAMPER 七种变换算子

// 对既有方案逐个套用变换算子，机械地榨出新形态
Substitute 替换Combine 合并Adapt 改造 Modify 调整Put to other use 挪用Eliminate 删除Reverse/Rearrange 反转·重排
SSubstitute · 替换运行时 YAML 解析换成编译期生成静态表——动态与性能兼得
SSubstitute · 替换reqwest 换 ureq（同步、极小二进制）——CLI 场景 async 并非必需
CCombine · 合并spec 用 include_str! 打包进二进制 + --spec 参数允许开发时覆盖
CCombine · 合并缓存层一层两用——spec 缓存 + HTTP 响应缓存（etag）
AAdapt · 改造同一 IR 顺便暴露 MCP server 模式（outline mcp serve）——CLI 和 MCP 一份代码
MModify · 调整用 overlay 文件给 spec 加 x-cli 扩展（别名、输出模板、示例），不 fork 上游 spec
PPut to other use · 挪用引擎 crate 做成通用库，任何 RPC 风格 OpenAPI 都能用——outline-cli 只是第一个实例
EEliminate · 删除运行时彻底不碰 OpenAPI——CI 里把 spec 编译成紧凑 command manifest（JSON），CLI 只读 manifest
EEliminate · 删除v1 不要配置文件——只用环境变量，config 后加
RReverse · 反转不是 CLI 读 spec，而是 spec 测 CLI——从 spec examples 生成契约测试
RRearrange · 重排惰性解析——只反序列化本次调用的那一个 operation，启动 <10ms
MModify · 调整shell 补全由 spec 生成（clap_complete 动态）——子命令和 flag 名都能补

technique/05 - morphological --matrix

#05 形态学分析 Morphological

// 把设计空间切成维度 × 取值，再在矩阵里连线选组合
先画维度矩阵再选型：{spec 处理: 运行时解析|编译期 IR|完全 codegen} × {命令形态: 平铺 rpc|资源-动词|混合} × {输出: json|table|md|模板}。三条连线 A/B/C 就是三种命运。
维度取值空间（A / B / C 为三种组合的连线）
spec 处理运行时解析 · A编译期 IR · B完全 codegen · C
命令形态平铺 rpc · A资源-动词 · B薄 clap 前端 · C混合
输出json · A富输出 · Btablemd模板

组合 A "解释器"

运行时解析 + 平铺 rpc + json 输出 = 一个周末的 MVP

组合 B "产品"

编译期 IR + 资源-动词命令 + 富输出 = 真正拿得出手的版本

组合 C "库优先"

progenitor 生成类型安全 client + 薄 clap 前端 = 最类型安全但失去动态性

参数形态复杂嵌套参数走 --body @file.json 直通，spec 驱动的 flag 只管标量
输出形态--template 用户自定义 minijinja 模板
输出形态markdown 终端渲染用 termimad/syntect 高亮
认证形态先 API key，OAuth device flow 留给以后
发行形态cargo-dist 一个配置出 brew tap + shell 安装器 + MSI
spec 更新随版本 vendored | spec sync 手动拉 | 每周自动检查提醒，三选一或组合
命令命名API 原名（documents.info）为规范名，人体工学别名（docs info）做层叠
配置层叠flag > env > 项目 .outline.toml > 用户配置——项目级配置可把 repo 绑定到某 collection
technique/06 - what-if --branch-all

#06 What-If 场景 条件分支

// 把未来可能发生的每种情况写成 if 分支，逼出应对策略
if 如果 Outline 破坏性改 API？
每个 CLI 版本 pin spec 版本 + outline doctor 对比线上 API 与缓存 spec 的差异
if 如果用户有 3 个 workspace？
命名 profile + --profile，类 AWS_PROFILE
if 如果离线？
文档 read-through 缓存支持离线读（写入队列可能过度设计，记下不做）
if 如果文档超大？
流式进 pager，--raw 给管道
if 如果在 CI 里用？
--json + 稳定退出码 + env 认证，文档给 CI 配方
if 如果要批量操作？
outline docs export --collection X --format md --out dir/，建立在分页引擎上
if 如果有管道输入？
stdin 做文档内容：cat notes.md | outline docs create --title Notes
if 如果 API 新增端点？
spec sync 后新操作自动出现在 outline api list——动态架构在这里回本
if 如果两个进程并发写缓存？
原子 rename / 文件锁，损坏则自愈重解析
if 如果是自托管企业版 Outline（不同 base URL + 旧 API）？
profile 级 base URL + 尝试从服务器协商 spec

#07 六顶思考帽 浓缩轮换

// 白=事实 · 黑=风险 · 黄=乐观 · 绿=创意 · 红=直觉，轮流戴帽发言
白·事实Outline 官方 spec 在 github.com/outline/openapi，社区维护——下注前先验新鲜度，契约测试不可省
黑·风险schema 里的 oneOf/anyOf 很难映射成 CLI flag——这类操作回退到 --body JSON
黑·风险完全 codegen 会让二进制膨胀；IR 解释保持 ~5MB 小体积
黄·乐观Rust 恰好是 CLI 最优语言——单二进制、瞬时启动、交叉编译容易，选型无悔
黑·风险限流按用户算，批量导出会撞——client 里放全局令牌桶节流
黄·乐观项目天然是学 Rust 的好素材，引擎/UX 分层架构清晰
绿·创意以后加 outline tui——ratatui 做 collection 树浏览器
红·直觉全动态很"聪明"，但你天天想用的是精心策划的 UX——直觉投混合方案
黑·风险搜索结果的终端展示（高亮、上下文行，像 ripgrep）需要专门设计
白·事实附件上传是两步协议（attachments.create → S3 POST），通用引擎覆盖不了——预算约 5 个手写特例命令
technique/08 - ulimit --creative

#08 资源约束 Resource Constraints

// 像 ulimit 一样给项目上硬限制：时间、依赖、用户数、注意力，看约束逼出什么设计
--time=周末周末 MVP：硬编码 5 个命令（auth info / docs search / info / create / collections list）先验证手感，再建引擎
--yaml=0约束"运行时零 YAML"：先只用 documents.* 子集跑通 build.rs IR 管线
--deps=4依赖最小化：核心四件套 clap + reqwest + serde + anyhow，其余克制
--users=1010 用户约束：跳过 keyring，只 env var + README 快速上手，一周内发布迭代
--users=10001000 用户约束：outline doctor --bundle 生成无隐私调试包用于 issue 报告
--docs=1源文档约束：CLI 参考文档从同一 IR 生成（spec → man page / mdbook）——一份源三种产物
--test=golden测试约束：wiremock + spec 生成的 fixture；输出渲染用 golden file 测试
--render=v1省渲染省时法：v1 直接打印原始 markdown（本来就可读），花哨渲染 v2
--name=短命名约束：查 crates.io/brew 上 outline 是否冲突；日常敲的短名很重要，考虑二进制叫 otl
--focus=6cmd注意力预算：90% 使用集中在 6 个命令（search/view/create/update/collections/export）——抛光这 6 个，其余走 api 裸调
